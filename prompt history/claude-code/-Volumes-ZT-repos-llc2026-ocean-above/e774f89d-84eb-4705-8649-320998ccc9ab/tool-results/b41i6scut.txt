## Priority / motivation

**P0 functional requirement**: Ocean Above users must be able to stop an in-progress streamed Agent run. Stopping only the browser's SSE fetch is not sufficient: today `Agent.stream_turn()` creates a background `asyncio.Task` which intentionally continues after the client disconnects. A deliberate Stop must stop further model/tool work and free capacity safely. Ordinary network disconnection should continue to preserve current recovery behavior.

Research references:
- Vercel AI SDK `useChat().stop()` + server abort propagation: https://github.com/vercel/ai/blob/main/content/docs/06-advanced/02-stopping-streams.mdx
- OpenAI Agents SDK streamed `cancel(mode="immediate"|"after_turn")`: https://openai.github.io/openai-agents-python/streaming/
- LangGraph disconnect `cancel|continue` vs checkpointed HITL interrupt: https://github.com/langchain-ai/langgraph/blob/main/libs/sdk-py/langgraph_sdk/schema.py
- Pi agent abort signal to cooperative tools: https://github.com/earendil-works/pi

## Current source to inspect

- `backend/app/agent/loop.py`: `stream_turn()` creates `_run` task + event queue; `_events()` decoupled from task; `_steps()` can perform many tools; `_llm_step()` uses `aclosing`; `_drain()` tracks in-flight `asyncio.to_thread()` calls and preserves conversation locks; `_finish()` persists and presents cards.
- `backend/app/agent/llm.py`: streaming `httpx.AsyncClient.stream`, close/abort required.
- `backend/app/api/routes.py`: streaming POST, authenticated conversation ownership; separate `POST /quotes/{id}/book`.
- `frontend/src/lib/api.ts`: `sendMessage(..., signal?: AbortSignal)` already accepts a signal.
- `frontend/src/app/chat/page.tsx`: sends SSE, disables Send while generating, reloads server state on normal/failed completion; no explicit Stop.
- `backend/app/agent/concurrency.py`: global/per-user turn slots, shielded thread work and 30s bounded drain.
- `backend/app/airline/service.py`: booking confirmation and B1–B7 are separate; never cancel an already submitted booking transaction via Agent Stop.

## Semantics (must be explicit)

1. **User Stop** = cancel current Agent run; no new LLM calls or new tools after cancellation is observed; close in-flight model HTTP stream, preserve already completed tool results and the validated partial response; settle storage safely and free lock/turn slot.
2. **Network disconnect / closed tab / transient SSE failure** = continue background run and persist final result, maintaining current behavior. Do not infer user Stop from `request.is_disconnected()` alone.
3. **Stop ≠ rollback booking**. A separate Confirm Booking HTTP action and committed ticket are immutable, never silently reverted. Any already-running synchronous tool/DB transaction must be allowed to settle safely before releasing relevant locks; a stopped turn cannot mint fresh booking authority for unseen information.
4. **MVP: immediate cooperative Stop**, not pause/resume, rewind, regenerate, or LangGraph-style checkpoint interruption. Document graceful `after_turn` as an optional future mode.

## SDK evaluation / optional migration (2026-11-24 addendum; requested by owner)

**Do not treat the hand-written Agent Loop as a permanent constraint.** We actively prefer an established SDK if it reduces implementation/maintenance effort and offers correct native cancellation/streaming. Compare *Agent SDK* vs *model API SDK* (the latter does not implement an agent loop).

| Candidate | Rationale | Important trade-off |
|---|---|---|
| **OpenAI Agents SDK (Python)** — first POC | Python fits existing FastAPI backend; Runner.run_streamed() + result.cancel() / cancel(mode="after_turn"), function tools, tracing, built-in run controls | Extra dependencies vs raw client; non-OpenAI DeepSeek endpoint must be configured through OpenAIChatCompletionsModel/AsyncOpenAI; ensure provider compatibility and explicit tracing/exporter privacy |
| **Pydantic AI Slim [openai]** — comparison POC | Python, provider abstraction, run cancellation/stream interruption, typed tool validation, optional slim deps | Map partial tool calls, run history, model profiles and current custom ReplyGuard/quoting semantics explicitly |
| **openai-python** — minimal migration | Official model SDK; easier replacement for custom httpx streaming, parsing and retries | No automatic tool-dispatching agent loop or run registry; cannot alone solve user Stop |
| **Vercel AI SDK** — reference / TS alternative | Strong React useChat stop/stream UX, provider ecosystem | JS/TS-first; migrating backend agent orchestration from FastAPI to Next.js is a larger cross-language rewrite, not justified solely for Stop |

   - If testing storage growth, seed increasing counts of messages/tool logs/quotes/tickets independently of city count.
4. **Load sweep**: 1 / 5 / 10 / 25 / 50 / 100 concurrent clients, warm-up + repeated measured intervals; hold workload distribution, hardware and DB size fixed. Record Python/SQLite versions, CPU, filesystem type, host/container details. Include realistic separate LLM-latency scenario as a second end-to-end benchmark, not the only measurement.
5. **Metrics**: request throughput, end-to-end p50/p95/p99 by endpoint, SQLite writer-lock wait and transaction-hold p50/p95/p99, booking `_recheck` p50/p95/p99, `SQLITE_BUSY`/5xx rate, CPU/memory/IO, WAL growth/checkpoint latency, data-integrity errors (double bookings, quote/ticket status mismatch).
6. **Tools**: simple Python `httpx` + `asyncio` workload (or Locust/k6) plus in-process store microbenchmark; first benchmark current implementation, then compare optimizations under identical workload and SLOs. Include run instructions and machine-readable results, not only screenshots.

## Decide whether to migrate

- Keep SQLite if correctness holds and the observed writer-lock wait, booking latency, error rate and sustained write throughput meet the explicitly stated target SLO on expected workload.
- First try shortening write transactions: consider computing expensive route validation **before** acquiring `app.db` writer lock, but preserve atomic confirmation and protect the TOCTOU boundary (e.g., consistent version/fingerprint verification inside transaction). Do not change this blindly; correctness and booking invariants B1–B7 are mandatory.
- Consider batching/asynchronously exporting noncritical telemetry logs or separating high-volume observability data, without degrading conversation history integrity.
- Move to PostgreSQL when sustained write contention, multi-instance deployment, or operational requirements justify it. PostgreSQL row locks help with different quotes, but migrations also require revisiting conversation-level locking, idempotency, schema/transactions and operational overhead. Do not conflate a graph DB or MCP with solving app.db writer contention.
- Publish a small decision table with **measured** before/after results and rationale. No arbitrary QPS threshold should be portrayed as a fact.

- Documentation clearly distinguishes WAL, per-conversation locks and single-worker restrictions.
- A reproducible, isolated benchmark harness or detailed ready-to-run plan with workload generators and metrics; report measured results if executed, otherwise explicitly label as unmeasured.
- B1–B7 and regression tests remain green after any instrumentation or optimization.
- No unnecessary switch to PostgreSQL; log future migration as a conditional decision.
